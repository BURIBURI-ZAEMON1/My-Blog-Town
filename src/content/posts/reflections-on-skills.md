前段时间自己写了几个 skill,进行了持续优化,并把其中我认为效果不错的进行了开源.在这个过程中我慢慢积累了一些自己的理解,所以想用这篇博客记录一下我对炼制 skill 的理解.那么很显然这篇的标题取得有些标题党,因为我只是谈一下我自己的理解.

## 从一个具体 skill 开始

我写的第一个 skill 是[idea-thinking-skills](https://github.com/BURIBURI-ZAEMON1/idea-thinking-skills)中的 idea-refiner.

写这个 skill 的起因其实是 grill-me.当时我经常使用它来打磨自己的 idea,但它的表现并不完全符合我的需求,所以我决定自己做一个专门用于完善 idea 的 skill.

最开始写的时候,我对 skill 的理解非常直接:先想清楚自己认为比较好的工作流程,再把这个流程写给 AI.于是我定义了几个 workflow,解释每一步的目的和要求,然后让 AI 根据我的想法进行整理,最后把整体拆分成 `SKILL.md` 和 references.

这个过程本身没有什么问题,而且确实可以快速得到一个能工作的初版.真正的问题在于,我当时把“我认为合理的工作方式”和“这个任务必须遵循的工作方式”混在了一起.

当一个 workflow 被写得足够详细时,AI 通常会非常认真地执行它.但它不会自动知道这个 workflow 只是我的一个假设,更不会主动判断这个假设是否已经不适合当前任务.因此,如果最开始的流程有偏差,后面的优化很可能只是让这个偏差变得更加完整.

这也是我后来持续优化甚至重新设计这个 skill 的起点.

## skill 不只是提示词,也不只是流程

我现在不太愿意把 skill 只理解成"提示词工程".提示词当然是它的一部分,但一个真正会被反复使用的 skill,还需要处理很多提示词之外的问题.

首先是范围.它需要让 Agent 知道自己应该在什么情况下被使用,又不应该把所有相邻任务都接管过来.如果范围过宽,skill 会变成什么都想管的总管;如果范围过窄,它又可能只适用于作者写示例时想象的某个场景.

其次是行为.一个 skill 不只是告诉 Agent“输出什么”,还需要影响 Agent 在过程中如何观察问题、如何做判断、什么时候继续推进、什么时候停下来向用户确认.

再次是结果的生命周期.如果一次任务只是生成一段文字,输出本身可能就够了.但很多 skill 会经历多轮对话,会产生中间结论、研究结果、未解决问题和后续输入.这时,skill 还需要考虑哪些内容应该被保留,怎样被下一次对话继续使用.

## 大模型能力提升后,skill 的价值会变化

在最开始写 skill 时,我下意识地认为规则越具体越好.因为模型有时无法稳定完成复杂任务,所以我会把任务拆成很多步骤,规定每一步要关注什么,甚至规定应该用什么样的格式继续.

这种方式在某些情况下确实有效.它可以减少模型漏掉明显要求的概率,也可以让一个本来很混乱的任务先拥有基本结构.但模型能力提升后,同样的做法可能产生相反的效果.

现在的 Agent 已经可以自己完成很多过去需要写进 skill 的事情:

- 从模糊描述中提炼出主要问题;
- 根据上下文补齐低影响细节;
- 自行比较多个方向;
- 研究相关资料并整理结果;
- 判断当前最值得继续讨论的问题;
- 根据目标调整输出形式.

如果 skill 仍然把这些事情全部写成固定步骤,就可能限制模型本来已经具备的判断能力.它会越来越像一份很长的操作手册,而不是一个能够适应不同情况的工作框架.

这并不意味着 skill 会变得没有价值.相反,skill 的重点会逐渐从“补充模型不会的能力”,转向“规定模型在这个场景里应该怎样使用自己的能力”.

一个能力很强的 Agent 仍然可能做出不符合预期的行为.它可能过度主动,把自己补全的内容当成用户已经确认的结论;也可能过度谨慎,把所有小问题都交给用户;还可能为了追求完整而输出大量低价值内容,或者因为过早判断任务已经足够明确而遗漏高影响的未知.

因此,skill 更应该明确的是:

- 哪些问题值得优先关注;
- 哪些内容可以由 Agent 自行补全;
- 哪些判断必须交给用户;
- 什么情况下需要检查遗漏;
- 什么情况下应该停止当前路径并重新判断;
- 最终结果需要以什么形式交给后续工作.

这也是为什么我现在不再用“规则越多越完善”来评价一个 skill.在模型能力较弱时,增加规则可能提高稳定性;但在模型能力提升后,同样的规则也可能造成过拟合,让 Agent 只能沿着作者预先想好的路径工作.

## 是否需要固定工作流

idea-refiner 的第一版就是一个很明显的反面例子.当时我认为,一个尚未成熟的 idea 可以按照“研究相关对象、分析风险、确认核心定义、设计方案、整理文档”的顺序逐步完善.

这个顺序看起来很合理,也确实能覆盖不少问题.但实际使用后,我发现它有几个副作用.

第一,用户会被带入一个预先设计好的问题空间.每一轮都在回答“现在应该确认什么”,而不是先判断“当前最值得解决的问题是什么”.

第二,原本应该集中讨论的一个重要矛盾,很容易被拆成很多小问题.用户每次只回答一个选项,表面上推进得很稳定,但长期下来会越来越像填写问卷.

第三,Agent 提供的选项会逐渐变成隐形的方向控制.用户看似一直在做选择,实际上可能只是在几个由 Agent 预先整理好的方向中选择.如果这些方向本身已经带有 Agent 的假设,用户就很难重新表达一个完全不同的想法.

我并不是因此认为流程没有用.复杂任务仍然需要结构,但结构应该更像护栏和检查点,而不是一条不允许偏离的轨道.更稳妥的做法是规定任务需要覆盖哪些重要维度,再让 Agent 根据当前上下文决定顺序和深度.

## 怎样开始炼制一个 skill

我认为制作 skill 的第一步应当是先把目标场景说清楚.

至少需要先回答几个问题:

- 这个 skill 要帮助谁完成什么任务;
- 用户通常会以什么状态进入这个任务;
- 任务的成功结果是什么;
- 哪些地方最容易失败;
- 哪些事情用户必须亲自决定;
- 哪些事情 Agent 应该主动完成.

这里的重点不是把所有情况都列完,而是找到这个 skill 真正要改善的失败模式.比如,用户说“帮我完善一个 idea”,这还不够具体.需要进一步确认,你想解决的是想法太模糊、缺少研究、容易遗漏关键问题、无法形成文档,还是用户不想被 AI 带着走.

不同失败模式会对应完全不同的 skill.如果连要改善什么都没有说清楚,后面很容易变成不断堆规则.

在此基础上,我倾向于先写一个足够小的初版.它不需要覆盖所有边界,但应该能在真实场景中完成一次完整任务.初版的目的不是证明设计已经正确,而是尽快暴露错误假设.

如果一开始就试图把所有例外、所有阶段和所有输出格式都写进去,得到的往往是一份看起来很专业、但没有经过使用验证的说明书.这样的 skill 可能很完整,却不知道哪些规则真正有价值.

## 优化不是不断添加规则

我把优化分成两部分交错进行:

1. 真人在真实对话中使用,观察结果和过程;
2. 用多个 Agent 对规则、结构和典型场景进行检查.

真人使用最容易发现的是体验问题.比如对话是否过长,用户有没有被迫回答太多小问题,Agent 是否过早替用户做决定,某个输出是否虽然形式正确但实际没有帮助.

多 Agent 检查更适合发现结构问题.比如规则之间是否冲突,某个要求是否被后面的要求覆盖,某个状态有没有定义出口,输出格式是否足够稳定,不同 reference 之间有没有互相矛盾.

两者不能互相替代.自动化检查很擅长在已有框架里找缺口,却不太擅长主动怀疑框架本身.如果我把 workflow 拆成六个步骤,自动化 Agent 很容易逐个检查这六步有没有缺规则,然后继续补充内容.这样可以让 skill 越来越完整,却不一定让它越来越好.

所以每次发现问题后,我现在会先追问一层:这是某条规则的问题,还是整体设计的问题?如果只是局部问题,可以补一个约束;如果多个问题都指向同一个前提,就应该重新检查这个前提,而不是继续打补丁.

真正有效的优化有时不是增加一条规则,而是删除一个不再必要的步骤,放宽一个过于具体的要求,改变输出责任,或者直接承认原来的 workflow 不适合所有场景.

## 需要重点测试在于“会不会走偏”

普通软件通常可以通过输入和输出判断功能是否正常.过程型 skill 则复杂一些.它即使最后生成了一份看起来完整的文档,中间过程也可能存在严重问题.

比如 Agent 可能通过连续提问把用户带到一个并非用户真正想要的方向,最后仍然输出一份结构完整的结果.如果只看最终文档,这个问题很难被发现.

因此,我认为至少需要同时观察三件事:

- 最终产物是否满足任务目标;
- 对话过程是否自然,是否产生了不必要的负担;
- 用户是否仍然拥有关键决策权.

还需要准备不同类型的测试场景.不能只用作者最熟悉、最容易成功的例子,还应该测试:

- 输入非常模糊的情况;
- 用户明确拒绝 Agent 默认方向的情况;
- 任务中途改变目标的情况;
- 需要多轮交接和持久化的情况;
- 关键条件没有被用户主动提到的情况.

最近一次重制版本的测试就暴露了一个细节:skill 要求输出分组进度,但 Agent 可能把每一道具体问题都做成一行 checklist,也可能只用一段普通文字概括进度.从静态规则来看,它似乎完成了要求;从真实使用来看,它们表达的是两种完全不同的体验.

这类问题很难只靠审阅文字提前消灭,必须让 skill 在真实对话中运行.因此,对过程型 skill 来说,真人试用不是上线后的附加检查,而是炼制过程本身的一部分.

## 什么时候应该重制,而不是继续优化

skill 迭代到一定程度后,最容易出现的问题是“修补惯性”.每次发现一个问题,就继续在原来的结构上加一条规则;每次出现例外,就再增加一个分支.最后 skill 变得越来越长,但真正的核心假设从来没有被重新检查.

我认为出现下面几种情况时,就应该认真考虑重制:

- skill 的核心价值割裂或极易被取代
- 大量问题都需要绕过原有 workflow 才能解决;
- 新增规则经常和旧规则冲突;
- Agent 经常完成了形式要求,却没有完成任务目的;
- 用户体验问题无法通过减少几轮提问解决;
- skill 的主要价值已经从“帮助完成任务”变成“维持自身的复杂结构”;
- 原来假设的模型能力、使用场景或用户需求已经发生变化.

重制并不意味着之前的内容全部作废.经过多次使用后,原 skill 中仍然有很多有价值的东西,比如已经发现的失败模式、真实场景中的测试记录、对输出质量的判断标准.这些内容可以作为新版本的材料,但不应该因为已经写过,就自动继承原来的 workflow.

我后来没有简单地继续优化旧版 idea-refiner,而是开始考虑重新设计并制作成全新的 idea-catalyst,就是因为出现了这等问题,并在我考虑后认为核心思路应当发生转变才能真正的解决问题.

## 利用 Agent 炼制 skill 的一些特殊心得

除了上面讲到的这些比较泛的理解,在炼制 skill 的经历中我还得到一些独特的心得.我认为这些心得的确能让一个 skill 的炼制过程变得更顺畅,或者使 skill 效果获得提升:

- 在炼制及优化过程中察觉的潜在问题或新主意,不一定需要立即告知你的 Agent.因为这些考虑可能会提前影响AI的注意力,导致炼制方向提前出现漂移,甚至 AI 会为了杜绝你提到的风险点极力克制 skill 的设计,导致走向另一个极端.我认为这些想法可以记录在一个独立区域(只有你自己看到),并由你自己判断当前时机是否应该向你的 Agent 提出这个观察(通常是测试后)
- 一个词的区别可能就会导致 skill 的效果出现相当大的不同.AI 对看似相近概念的描述可能会产生很大差别,虽然这会根据模型不同而产生差异,但还是可以说有些用词会是更合适的.这一点Matt Pocock 也提到过,我在优化 idea-catalyst 时也的确见识到了这一点,两个版本之间只改变了一个表述,就在多轮测试中表现出明显差异.所以有时候skill 的表现好坏不一定在规则上,还有可能在表述上
- 现在在 skill 中进行过多重复宽泛的反向约束可能反而会起到副作用.一是大部分情况下多余,二是可能会让 Agent 产生过度理解,过度克制,反而降低表现.比起反向约束,我认为更好的方式可能是上一点提到的改表表述
- 尽量不要只让设计 skill 的 Agent 自己测试、评价自己的修改.它已经知道这次想解决什么问题,测试时可能会刻意注意这个问题,最后把符合预期的表现当成修改有效的证据.我更愿意保留一部分未经提示的真实试用,或让不了解本轮修改意图的 Agent 从结果和对话过程出发检查.这样才更容易发现新规则没有解决的问题,以及它引入的新问题.

## 结语

现在写 skill 是个很轻易的事,利用 Agent 能很轻易的让某一个思考,某一段项目经验就变成一份 skill.的确这样一份 skill 就已经足够个人使用了,但还不能具备作为一个好用的 skill 应该有的潜质.

写一份好的 skill,我认为需要自己在这个方向上有充分经验和感悟,才能定下来 skill 核心路线,以及才有能力评判这个 skill 是否好用(我的idea-refiner首版就是这么被推翻的,不够有产品思维和感悟).并且知道哪些地方应该固定,哪些地方应该留给模型判断,以及什么时候应该停下来怀疑自己正在维护的结构.

skill 的适用性不是一成不变的.模型能力会继续变化,使用场景会变化,用户对 AI 的期待也会变化.一个今天需要写进 skill 的约束,明天可能已经变成模型自然具备的能力;一个今天看起来足够稳定的 workflow,也可能在新的任务里变成限制.我们能看到最开始的 skill 和现在的 skill 之间有相当大的区别,就像之前 GPT 5.6sol 出现的时候非常多人认为之前几乎必备的 superpower 已经成为累赘,随着模型能力增强,skill 的价值会发生改变,甚至可能会被直接淘汰掉.

所以我觉得 skill 的炼制可能也更像是一种持续的工程实践:先提出假设,再通过真实使用验证,最后保留真正有价值的边界.
